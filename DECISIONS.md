# Архитектурные решения

## Общая архитектура

**Монорепо, два артефакта: core + agent.**
Core — ядро (FastAPI + Celery + Mongo) на VPS в Польше. Agent — тупой сенсор
на машине в РФ. Разные зависимости, разные деплой-таргеты, но один репозиторий —
видно всю систему целиком.

**Модульный монолит, не микросервисы.**
Домены изолированы папками (resources/measurements/probing/verdicts), но живут
в одном процессе. Микросервисы решают организационную проблему (много команд),
которой у соло-разработчика нет. Платить их цену (сеть, распределённость) без
выгоды — оверинжиниринг. Границы между доменами прочерчены — если один
понадобится вынести, вырежется по границе. Монолит, готовый к распилу.

**MongoDB, а не Postgres+JSONB.**
Сознательный выбор ради документной модели: замеры (details) разнородны по
источникам — у внешнего пробника TLS-серт и редиректы, у внутреннего агента
тип ошибки и RTT. Честно: Postgres+JSONB тоже справился бы и при сильном
SQL-бэкграунде был бы дефолтным выбором. Mongo взят, чтобы пощупать документную
модель. Цена — нет foreign keys, целостность связей на уровне приложения.

## Точки обзора (vantage points)

**Точка обзора — отдельная сущность, замер ссылается через vantage_id.**
Не хардкод "internal/external". Причина: фильтрация в РФ НЕ однородна по
операторам (ТСПУ настроены неравномерно, региональность). "Заблокировано на
МТС" != "заблокировано на Билайне" — это основной сигнал продукта, не шум.
Модель рассчитана на N точек, задеплоено две (РФ-ноут + Польша). Метаданные
точки (operator, network_type, region) заполняются вручную в конфиге агента.

**MVP: две свои точки. Прицел: краудсорс (как OONI).**
Автоопределение оператора по IP и регистрация чужих агентов — припарковано на
будущее. Модель уже поддерживает, реализация отложена, чтобы не раздуть скоуп.

## Агент

**Тупой сенсор: снимает показания, не выносит вердиктов.**
Агент = метеостанция (мерит и шлёт цифры), ядро = вычислительный центр (сводит
и решает). "Померить" — снять показание, это не логика. "Вердикт" — сравнить
две точки и решить "заблокировано", это логика, живёт в ядре. Замер обязан
делаться машиной в РФ, потому что блокировку видно только оттуда, где она
применяется — это физическое местоположение, не переносится в ядро.

**Транспорт агент→ядро: HTTPS POST на публичный эндпоинт.**
Агент за NAT, исходящий HTTPS — единственное, что гарантированно пройдёт и не
палится как подозрительный трафик.

**Аутентификация: bearer-токен на MVP → HMAC+timestamp в security-проход.**
Bearer достаточно поверх HTTPS (канал шифрован). HMAC — эволюция: секрет не
светится в каждом запросе и в логах (в отличие от bearer), timestamp защищает
от replay. Граница доверия нужна не потому что машина ненадёжна (ноут свой),
а потому что эндпоинт публичный и не отличает своих по факту подключения.

**Список ресурсов агент тянет из ядра, кеширует, обновляет редко.**
Централизованное управление (добавил ресурс в ядре — агент подхватил) без
похода на машину в РФ. Список меняется медленно — минутная задержка не критична.

**Агент буферизует замеры при недоступности канала.**
Из РФ ядро может быть временно недостижимо (ирония: монитор блокировок сам
может быть заблокирован). Копит локально, досылает при восстановлении. Именно
в моменты, когда всё режется, данные интереснее всего — терять нельзя.

## Модель данных

**Четыре коллекции: vantage_points, resources, measurements, verdicts.**

**Вердикт считается на записи, в историю пишутся только переходы.**
Периодическая задача сводит свежие замеры, пишет запись ТОЛЬКО при смене
вердикта (available -> blocked). Не плодит одинаковые. История переходов —
таймлайн "в 14:00 заблокировали", а не снимок состояния. Мини-event-sourcing.
Продукт про изменения во времени, поэтому история обязательна.

**Идемпотентный приём замеров через клиентский measurement_id.**
Агент генерит UUID замера, ядро дедуплицирует. Агент при глюке сети может
переслать замер дважды — ядро по id поймёт "уже видел".

**"Агент офлайн" != "ресурс недоступен".**
Отдельное состояние no_data. Свежесть замера через TTL. Нет данных изнутри —
не можем судить, это не "заблокировано".

## Домен resources

**Слоистая архитектура: router -> service -> repository, схемы на границах.**
Router — HTTP (коды, маршруты). Service — бизнес-логика. Repository —
единственный, кто знает про Mongo. Router не ходит в базу через голову сервиса.
Порядок постройки обратен потоку данных: строим снизу вверх (schemas->router),
данные текут сверху вниз. Преобразования живут на границах, которые данные
пересекают: slug->_id на входе в базу (repository), dict->ResourceOut на выходе
к клиенту (router).

**Две схемы: ResourceCreate (приём) и ResourceOut (отдача) — граница полномочий.**
Create содержит только то, что клиент вправе задать. Клиент физически не может
прислать _id/enabled — их нет в схеме приёма. Защита от mass assignment: клиент
не должен присваивать серверные поля (enabled, is_verified и т.п.).

**_id = slug: клиент предлагает, сервер валидирует (путь Б).**
Не Mongo-ObjectId (нечитаемо в логах), не слугификация из name (коллизии,
транслит, id становится заложником name). Клиент даёт короткий slug, сервер
проверяет формат (regex в схеме) и уникальность. Аналогия — username при
регистрации: юзер выбирает, сервер накладывает правила. Не mass assignment,
т.к. сервер контролирует правила.

**_id в Pydantic через alias.**
Python игнорирует поля с ведущим подчёркиванием. Поле зовётся id, alias="_id"
сшивает с формой Mongo/JSON.

**Двойная защита уникальности: проверка в сервисе + DuplicateKeyError в репо.**
Проверка get_by_id в сервисе даёт красивую 409 в 99% случаев, но НЕ гарантирует:
между проверкой и вставкой зазор, гонка (два запроса пройдут проверку и оба
вставят). Железная гарантия — уникальный индекс _id в Mongo. Репозиторий ловит
DuplicateKeyError и переводит в доменное ResourceAlreadyExists. Оба слоя нужны.

**Доменные исключения, не HTTPException в сервисе.**
Сервис кидает ResourceAlreadyExists (язык предметной области, про HTTP не знает).
Роутер ловит и переводит в HTTP 409. HTTP-коды — деталь представления, живут на
границе с HTTP. Иначе сервис нельзя вызвать не из HTTP (из Celery, CLI).

**enabled: мягкое выключение вместо удаления.**
Обходит проблему висячих ссылок (в Mongo нет FK — удалишь ресурс, замеры
осиротеют). enabled=false рвёт мониторинг, но сохраняет историю.
